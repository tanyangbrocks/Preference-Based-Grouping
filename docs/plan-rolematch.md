# RoleMatch — 自動分工工具 實作計畫

> 狀態：v0.1 已實作（2026-09-23），待確認問題採預設方案
> 建立日期：2026-09-23
> 專案名稱 `RoleMatch` 為暫定

---

## 一、需求摘要

| 角色 | 能做的事 |
|------|----------|
| **主辦方**（網站首頁） | 建立分組活動：名稱、敘述、截止時間（DL）、職位清單（每個職位的名額）→ 拿到邀請連結與 QR code |
| **組員**（邀請連結） | 看活動內容 → 排自己對各職位的志願序 → 為每個志願設定「渴望度」→ 截止前可以修改 |
| **系統** | 截止後自動分配。規則：志願序相同時，渴望度高的人優先；**任何人都不會被分到自己志願後半段的職位** |

**公正性要求**：
- 主辦方**看不到**任何人填了什麼
- 主辦方**無法操縱**分配結果

## 二、技術選型

| 項目 | 選擇 | 理由 |
|------|------|------|
| 框架 | **Next.js（App Router）+ TypeScript** | Vercel 原生支援；前後端（API Routes）放在同一個 repo |
| 部署 | **Vercel** | 需求指定 |
| 資料庫 | **Neon Postgres**（從 Vercel Marketplace 一鍵接） + **Drizzle ORM** | 免費額度夠用；需要交易／row lock，確保結算只做一次 |
| UI | Tailwind CSS + shadcn/ui | 手機優先（組員多半用手機掃 QR） |
| 拖拉排序 | `@dnd-kit/sortable` | 志願排序要能在手機上用觸控拖拉 |
| QR code | `qrcode`（前端產生 SVG/PNG） | 不需要後端服務，可以直接下載 |
| ID | `nanoid`（10 字元） | 短網址，而且不容易被猜到 |
| 測試 | Vitest | 分配演算法一定要有單元測試 |

**⚠️ 不用 Vercel Cron 觸發結算**：Hobby 方案的 Cron 一天只能跑一次，時間也不精準。改用**懶結算（lazy finalize）**：截止後第一個打開活動頁的人會觸發結算，結果寫進 DB 後就不再改變（見 §五）。

## 三、分配演算法（核心）

### 3.1 定義

- `m`：職位數；`n`：組員數
- 職位 `r` 的名額為 `cap[r]`，必須滿足 `Σcap ≥ n`
- 每位組員要排出**全部** `m` 個職位的志願序（1 = 最想要）
- **可接受範圍 K = ⌈m/2⌉**：每個人只會被分到自己的第 1～K 志願
  - 例：6 個職位 → 前 3 志願；5 個職位 → 前 3 志願
- **渴望度**：每人有 **⌈m × 3 ÷ 2⌉ 點**（例：4 職位 = 6 點、5 職位 = 8 點），自由分配到各志願（見 §3.4 為什麼一定要設預算）
- **多人職位**：每個職位由主辦方設定「最多 N 人」（`cap[r]`），同一職位可同時分給多人

### 3.2 演算法：逐輪志願 + 可行性檢查

```
invariant：剩下的組員，一定能在「各自前 K 志願 × 剩餘名額」內全部排進去（存在完美匹配）

for k = 1..K:
    候選 = 所有還沒分到的組員，各自的第 k 志願
    依（渴望度 ↓，平手用 seeded random）把候選排成一個全域順序
    for 候選 (member, role) in 順序:
        if role 還有名額 AND 暫時指派後 invariant 仍然成立:
            確定指派
        else:
            跳過（留給下一輪）

剩下還沒分到的人（理論上很少）→ 在前 K 志願內做 min-cost 匹配（cost = 志願序）
```

- **為什麼要做可行性檢查**：單純「第一志願先搶」（Boston 機制）可能讓某些人最後只剩後半段的職位。每一步都先確認「剩下的人還排得進前 K 志願」才確定指派，就能**保證**不違反「一半以下」的限制。
- 可行性檢查用二分圖最大匹配（Hopcroft–Karp，或拆名額後用 Kuhn 演算法）。一般分組大約 n ≤ 200，檢查 O(n²) 次也只要毫秒等級。
- 平手的 random 由活動建立時產生的 `seed` 決定，所以結果**可重現**（見 §五）。

### 3.3 無解時的處理（v0.2 修訂）

**只要存在任何一種讓所有人都落在前 K 志願的分法，就一定不放寬**（可行性檢查保證）。

真的無解時（例：4 個職位各 1 人，4 個人的前 2 志願全都是 A、B），**只放寬必要的最少人數**，而不是把所有人一起放寬：
1. 階段 A：依 seed 隨機順序逐一嘗試把每個人收緊到前 K；收不進的人才放寬。「能同時落在前 K 的人」構成 transversal matroid，所以貪心得到的就是最大人數，放寬人數 = 理論最小值（= n − 前 K 志願內的最大匹配數）
2. 階段 B：被放寬的人也盡量收緊（K+1、K+2…）
3. 由誰放寬由 seed 隨機決定；結果頁公開「有 x 人分到前 K 志願之外」，但不公開是誰

效能：200 人 × 20 職位、全員志願完全相同的極端情況約 1.6 秒（只在結算時跑一次）；一般情況約 20 ms。

### 3.4 渴望度為什麼要有預算

如果渴望度是 1～5 自由填，每個人都會填 5，這個欄位就失去意義。改成**固定總點數自由分配**（v0.2 起 = 職位數 × 3 ÷ 2，無條件進位）：
- 想全力爭取第一志願 → 把點數全押在第一志願
- 對排名沒那麼堅持 → 平均分配
- 渴望度只在「同一輪、搶同一個職位」時比較，所以押注有取捨，也有策略意義

### 3.5 沒填的人

截止時還沒提交的組員（若有名單，見 §八-Q3）→ 等所有已提交的人分配完後，**隨機**分到剩下的名額。

### 3.6 必須涵蓋的單元測試

- [x] 所有人第一志願都不同 → 全部拿到第一志願
- [x] 同一職位多人搶 → 渴望度高者得
- [x] 渴望度平手 → 同一個 seed 結果固定，換 seed 結果可能不同
- [x] 貪心會讓某人掉到後半段的情境 → 可行性檢查會擋下來
- [x] 無解情境 → K 正確放寬並標示
- [x] Σcap < n → 丟錯（實際在「加入」時擋：人數達總名額後拒絕新提交）
- [x] 隨機產生 1,000 組資料做 property test：每個人都被分配、沒有職位超額、每人名次 ≤ K′

## 四、資料模型

```
activities
  id              text PK (nanoid)
  title           text
  description     text
  deadline        timestamptz (UTC)
  host_token_hash text          -- 主辦方管理權杖（只存 hash）
  seed            text          -- 平手用亂數種子；結算後才公開
  seed_hash       text          -- 建立時就公開（commit）
  status          enum('open','finalized')
  relaxed_k       int null      -- 有放寬時記錄 K′
  created_at, finalized_at

roles
  id, activity_id FK, name, description, capacity, sort_order

submissions
  id, activity_id FK
  display_name       text
  member_token_hash  text      -- 組員編輯自己志願用
  ranking            jsonb     -- [{ roleId, rank, desire }]
  updated_at
  UNIQUE(activity_id, display_name)

assignments   -- 結算後寫入，之後不可再修改
  activity_id, submission_id, role_id, got_rank
```

## 五、公正性設計（主辦方看不到、改不了）

| 威脅 | 對策 |
|------|------|
| 主辦方偷看填寫內容 | API **沒有任何 endpoint** 會回傳別人的 `ranking`。主辦方後台只看得到「已提交人數」 |
| 組員偷看別人的填寫 | `GET submission` 只回傳持有 member token 的那一份 |
| 主辦方中途改職位來影響結果 | **收到第一份提交後**，職位清單和名額就鎖定 |
| 主辦方延後／提前截止 | 建立後**不能修改 DL**（或只允許在 0 份提交時修改） |
| 主辦方重新跑一次，挑自己喜歡的結果 | 結算只會執行一次：`UPDATE activities SET status='finalized' WHERE id=? AND status='open'` 搭配交易，結果寫進 `assignments` 後就不能再改；**沒有任何重新結算的 API** |
| 操縱平手的亂數 | 建立活動時就公開 `seed_hash`，結算後公開 `seed`，任何人都可以驗證 `hash(seed)` 有沒有被換掉 |
| 冒名替別人填寫 | 組員第一次提交時取得 member token（存在 localStorage）；同一個活動內不能重名（進階做法見 §八-Q3） |

> 誠實聲明：伺服器（也就是網站營運者）在技術上仍然看得到資料庫。上面這些設計能防的是**主辦方**，不能防**營運者**。如果以後需要，可以把演算法開源，並在結果頁附上可驗證的資訊。

## 六、頁面與 API

### 頁面

| 路徑 | 用途 |
|------|------|
| `/` | 主辦方建立活動表單（名稱、敘述、DL、職位 + 名額、動態增減） |
| `/a/[id]/host` | 主辦方後台：邀請連結、QR（可下載）、已提交人數、倒數、結果。權杖放在 URL fragment `#t=...`，前端讀取後存進 localStorage（fragment 不會送到伺服器，也不會留在伺服器 log） |
| `/a/[id]` | 組員頁：截止前 → 填名字、拖拉排序、分配渴望度（即時顯示剩餘點數）；截止後 → 顯示結果 |

### API（Next.js Route Handlers）

| Method | Path | 說明 |
|--------|------|------|
| POST | `/api/activities` | 建立活動，回傳 `id` 與 `hostToken`（只顯示這一次） |
| GET | `/api/activities/[id]` | 公開資訊、狀態、提交人數；**如果已過 DL 且還沒結算 → 觸發結算** |
| GET | `/api/activities/[id]/submission` | 讀自己的填寫（需要 member token） |
| PUT | `/api/activities/[id]/submission` | 新增或更新自己的填寫（驗證：排序完整、點數合計 = 100、還沒過 DL） |
| GET | `/api/activities/[id]/result` | 分配結果（見 §八-Q5 可見範圍） |

伺服器端驗證 DL 一律以**伺服器時間**為準，前端倒數只用來顯示。

## 八、待確認問題

| # | 問題 | 預設方案 |
|---|------|----------|
| Q1 | 渴望度用「100 點預算分配」還是其他方式？ | ✅ 已決定：總點數 = 職位數 × 3 ÷ 2（§3.4） |
| Q2 | 組員要排**全部**職位，還是只要排前 K 個？ | 排全部（UI 比較單純，演算法也用得到完整資訊） |
| Q3 | 組員身分：自由填名字，還是主辦方預先輸入名單讓組員選？ | 自由填名字 + 禁止重名。有名單的話可以防冒名和灌假帳號，也能知道誰還沒填 |
| Q4 | 主辦方可以在全員提交後**提前結算**嗎？ | 可以，但只限「有名單且全員已提交」的情況 |
| Q5 | 結果可見範圍：所有人都看得到完整分配表，還是每人只看到自己的？ | 完整分配表（姓名 → 職位），但**不顯示**每個人拿到第幾志願 |
| Q6 | 職位名額：只設上限，還是也要設下限（例：美術至少 2 人）？ | 只設上限，並要求 Σcap ≥ 人數；下限之後再加 |

## 九、v0.1 實作與計畫的差異（2026-09-23）

| 計畫 | 實際 | 原因 |
|------|------|------|
| Drizzle ORM | `@neondatabase/serverless` 直接寫 SQL；資料表在第一次請求時 `CREATE TABLE IF NOT EXISTS` | 只有兩張表，省去 migration 步驟；部署時不需要手動建表 |
| shadcn/ui | 純 Tailwind（`globals.css` 的 `@utility card/input/btn`） | 需要的元件很少 |
| `roles` / `assignments` 各自一張表 | 都用 jsonb 存在 `activities.roles` / `activities.result` | 建立後就不能改，不需要正規化 |
| 收到第一份提交後鎖定職位 | 建立後**完全不能修改**活動（沒有編輯 API） | 更簡單，也更難被操縱 |
| `GET /result` | 合併進 `GET /api/activities/[id]`（結算後才帶 `result`） | 少一次請求 |
| 本機開發 | 沒有 `DATABASE_URL` 時用 `.data/dev-db.json` | 不需要資料庫就能開發 |
| 渴望度 | 跟著**職位**移動（拖拉排序時點數跟著職位走） | 使用者的心智模型是「我給這個職位幾點」 |
| §3.5 沒填的人 | 未實作（Q3 採自由填名字，沒有名單就不存在「沒填的人」） | — |
| v0.1：無解時全體放寬到 K′ | v0.2：只放寬最少人數，由 seed 隨機決定是誰 | 使用者要求（§3.3） |
| 渴望度 100 點 | v0.2：職位數 × 3 ÷ 2 | 使用者要求 |
