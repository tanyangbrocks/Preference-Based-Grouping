# RoleMatch — 自動分工工具 實作計畫

> 狀態：v0.1 已實作（2026-09-23），待確認問題採預設方案
> 建立日期：2026-09-23
> 專案名稱 `RoleMatch` 為暫定

---

## 一、需求摘要

| 角色 | 能做的事 |
|------|----------|
| **主辦方**（網站首頁） | 建立分組活動：名稱、敘述、截止時間（DL）、職位清單（每個職位的名額）→ 拿到邀請連結與 QR code |
| **組員**（邀請連結） | 看活動內容 → 排自己對各職位的志願序 → 為每個志願設定「渴望度」→ 截止前可以修改 |
| **系統** | 截止後自動分配。規則：志願序相同時，渴望度高的人優先；**任何人都不會被分到自己志願後半段的職位** |

**公正性要求**：
- 主辦方**看不到**任何人填了什麼
- 主辦方**無法操縱**分配結果

## 三、分配演算法（核心）

### 3.1 定義

- `m`：職位數；`n`：組員數
- 職位 `r` 的名額為 `cap[r]`，必須滿足 `Σcap ≥ n`
- 每位組員要排出**全部** `m` 個職位的志願序（1 = 最想要）
- **可接受範圍 K = ⌈m/2⌉**：每個人只會被分到自己的第 1～K 志願
  - 例：6 個職位 → 前 3 志願；5 個職位 → 前 3 志願
- **渴望度**：每人有 **⌈m × 3 ÷ 2⌉ 點**（例：4 職位 = 6 點、5 職位 = 8 點），自由分配到各志願（見 §3.4 為什麼一定要設預算）
- **多人職位**：每個職位由主辦方設定「最多 N 人」（`cap[r]`），同一職位可同時分給多人

### 3.2 演算法：逐輪志願 + 可行性檢查

```
invariant：剩下的組員，一定能在「各自前 K 志願 × 剩餘名額」內全部排進去（存在完美匹配）

for k = 1..K:
    候選 = 所有還沒分到的組員，各自的第 k 志願
    依（渴望度 ↓，平手用 seeded random）把候選排成一個全域順序
    for 候選 (member, role) in 順序:
        if role 還有名額 AND 暫時指派後 invariant 仍然成立:
            確定指派
        else:
            跳過（留給下一輪）

剩下還沒分到的人（理論上很少）→ 在前 K 志願內做 min-cost 匹配（cost = 志願序）
```

- **為什麼要做可行性檢查**：單純「第一志願先搶」（Boston 機制）可能讓某些人最後只剩後半段的職位。每一步都先確認「剩下的人還排得進前 K 志願」才確定指派，就能**保證**不違反「一半以下」的限制。
- 可行性檢查用二分圖最大匹配（Hopcroft–Karp，或拆名額後用 Kuhn 演算法）。一般分組大約 n ≤ 200，檢查 O(n²) 次也只要毫秒等級。
- 平手的 random 由活動建立時產生的 `seed` 決定，所以結果**可重現**（見 §五）。

### 3.3 無解時的處理（v0.2 修訂）

**只要存在任何一種讓所有人都落在前 K 志願的分法，就一定不放寬**（可行性檢查保證）。

真的無解時（例：4 個職位各 1 人，4 個人的前 2 志願全都是 A、B），**只放寬必要的最少人數**，而不是把所有人一起放寬：
1. 階段 A：依 seed 隨機順序逐一嘗試把每個人收緊到前 K；收不進的人才放寬。「能同時落在前 K 的人」構成 transversal matroid，所以貪心得到的就是最大人數，放寬人數 = 理論最小值（= n − 前 K 志願內的最大匹配數）
2. 階段 B：被放寬的人也盡量收緊（K+1、K+2…）
3. 由誰放寬由 seed 隨機決定；結果頁公開「有 x 人分到前 K 志願之外」，但不公開是誰

效能：200 人 × 20 職位、全員志願完全相同的極端情況約 1.6 秒（只在結算時跑一次）；一般情況約 20 ms。

### 3.4 渴望度為什麼要有預算

如果渴望度是 1～5 自由填，每個人都會填 5，這個欄位就失去意義。改成**固定總點數自由分配**（v0.2 起 = 職位數 × 3 ÷ 2，無條件進位）：
- 想全力爭取第一志願 → 把點數全押在第一志願
- 對排名沒那麼堅持 → 平均分配
- 渴望度只在「同一輪、搶同一個職位」時比較，所以押注有取捨，也有策略意義

### 3.5 沒填的人

截止時還沒提交的組員（若有名單，見 §八-Q3）→ 等所有已提交的人分配完後，**隨機**分到剩下的名額。

### 3.6 必須涵蓋的單元測試

- [x] 所有人第一志願都不同 → 全部拿到第一志願
- [x] 同一職位多人搶 → 渴望度高者得
- [x] 渴望度平手 → 同一個 seed 結果固定，換 seed 結果可能不同
- [x] 貪心會讓某人掉到後半段的情境 → 可行性檢查會擋下來
- [x] 無解情境 → K 正確放寬並標示
- [x] Σcap < n → 丟錯（實際在「加入」時擋：人數達總名額後拒絕新提交）
- [x] 隨機產生 1,000 組資料做 property test：每個人都被分配、沒有職位超額、每人名次 ≤ K′

## 四、資料模型

```
activities
  id              text PK (nanoid)
  title           text
  description     text
  deadline        timestamptz (UTC)
  host_token_hash text          -- 主辦方管理權杖（只存 hash）
  seed            text          -- 平手用亂數種子；結算後才公開
  seed_hash       text          -- 建立時就公開（commit）
  status          enum('open','finalized')
  relaxed_k       int null      -- 有放寬時記錄 K′
  created_at, finalized_at

roles
  id, activity_id FK, name, description, capacity, sort_order

submissions
  id, activity_id FK
  display_name       text
  member_token_hash  text      -- 組員編輯自己志願用
  ranking            jsonb     -- [{ roleId, rank, desire }]
  updated_at
  UNIQUE(activity_id, display_name)

assignments   -- 結算後寫入，之後不可再修改
  activity_id, submission_id, role_id, got_rank
```

## 五、公正性設計（主辦方看不到、改不了）

| 威脅 | 對策 |
|------|------|
| 主辦方偷看填寫內容 | v0.7：主辦方後台**隨時**看得到已填寫名單（誰填了、第一次填寫時間、有沒有修改過），但看不到志願內容。v0.4：**結算後**主辦方後台可看到每人分到第幾志願、在該志願押的點數，以及抽籤／讓位／降低標準的事件紀錄（使用者要求）；仍看不到其他志願的排序。組員填寫頁明示此事 |
| 組員偷看別人的填寫 | `GET submission` 只回傳持有 member token 的那一份 |
| 主辦方中途改職位來影響結果 | v0.3：截止前**可以**修改（使用者要求）。改名稱／說明／人數上限不影響已填志願；新增或刪除職位會**清除所有人的填寫**（需主辦方確認）。人數上限加總不可少於已填人數。活動頁公開顯示「主辦方於 X 修改過」 |
| 主辦方延後／提前截止 | v0.3：截止前可修改（至少 1 分鐘後）；截止後完全不能修改 |
| 主辦方重新跑一次，挑自己喜歡的結果 | 結算只會執行一次：`UPDATE activities SET status='finalized' WHERE id=? AND status='open'` 搭配交易，結果寫進 `assignments` 後就不能再改；**沒有任何重新結算的 API** |
| 操縱平手的亂數 | 建立活動時就公開 `seed_hash`，結算後公開 `seed`，任何人都可以驗證 `hash(seed)` 有沒有被換掉 |
| 冒名替別人填寫 | 組員第一次提交時取得 member token（存在 localStorage）；同一個活動內不能重名（進階做法見 §八-Q3） |

> 誠實聲明：伺服器（也就是網站營運者）在技術上仍然看得到資料庫。上面這些設計能防的是**主辦方**，不能防**營運者**。如果以後需要，可以把演算法開源，並在結果頁附上可驗證的資訊。

## 六、頁面與 API

### 頁面

| 路徑 | 用途 |
|------|------|
| `/` | 主辦方建立活動表單（名稱、敘述、DL、模式、職位 + 人數上限、動態增減） |
| `/a/[id]/host` | 主辦方後台：邀請連結、QR（可下載）、編輯活動、**已填寫名單（誰填了／何時填的，v0.7）**、**執行分組按鈕（v0.7，隨時可按）**、結算後的分組明細＋事件紀錄。權杖放在 URL fragment `#t=...`，前端讀取後存進 localStorage（fragment 不會送到伺服器，也不會留在伺服器 log） |
| `/a/[id]` | 組員頁：截止前 → 填名字＋依模式填志願（拖拉排序＋押注／三級渴望度，或選第一志願＋勾選可接受）；截止後、分組完成前 → 顯示等待訊息；分組完成後 → 顯示結果 |

### API（Next.js Route Handlers）

| Method | Path | 說明 |
|--------|------|------|
| POST | `/api/activities` | 建立活動，回傳 `id` 與 `hostToken`（只顯示這一次） |
| GET | `/api/activities/[id]` | 公開資訊、狀態、提交人數（**不含**任何人的填寫內容） |
| GET | `/api/activities/[id]/submission` | 讀自己的填寫（需要 member token） |
| PUT | `/api/activities/[id]/submission` | 新增或更新自己的填寫（驗證依 §十模式而定；還沒過 DL 且活動未分組） |
| GET | `/api/activities/[id]/host` | 主辦方驗證＋公開資訊＋**已填寫名單**（v0.7）＋結算後的分組明細（不含其他志願排序） |
| PATCH | `/api/activities/[id]/host` | 主辦方編輯活動（v0.3；DL 前才可以）；增刪職位或換模式需 `resetSubmissions: true` 確認清空填寫 |
| POST | `/api/activities/[id]/host/finalize` | **主辦方手動執行分組（v0.7）**：截止時間到了不會自動做任何事，只有呼叫這支 API 才會結算；DL 前後都能呼叫，只會成功一次 |

伺服器端驗證 DL 一律以**伺服器時間**為準，前端倒數只用來顯示。

## 十、活動模式（v0.6，2026-09-25）

建立活動時三選一，之後可在後台編輯（換模式若已有人填寫，會清空所有填寫，需主辦方確認）：

| 模式 | 填法 | 可接受範圍 | 同志願搶同職位時 |
|------|------|------------|------------------|
| ① 押注渴望度（`bid`） | 排出所有職位志願序，⌈m×3÷2⌉ 點自由押注 | 前 ⌈m/2⌉ 志願 | 押得多的人優先 |
| ② 三級渴望度（`tier`） | 排出所有職位志願序，每個職位選 1／2／3 級 | 前 ⌈m/2⌉ 志願 | 級數高的人優先 |
| ③ 第一志願＋可接受（`pick`） | 選一個第一志願，其餘職位自由勾選「也可以」 | 第一志願或有勾選的職位 | 抽籤 |

**演算法怎麼統一處理三種模式**：`assign()` 從「志願序 + 渴望度」廣義化成「順位（rank）+ 渴望度」——同一順位可以對應**多個**職位（模式 ③ 的「有勾都算第二順位」），逐輪分配時同一順位內先比渴望度、再比「剩餘名額較多」（分散人潮）、再用 seed 隨機決定；`acceptableTier(mode, m)` 決定可接受範圍是 ⌈m/2⌉（①②）還是固定 2（③）。放寬演算法（§3.3）不需要改，因為它本來就是以「順位範圍」為單位。

模式 ③ 沒有「渴望度總和」的驗證，只要求剛好一個第一志願、其餘 `rank ∈ {2,3}`、`desire` 固定 0。

## 十一、手動分組與即時填寫名單、倒數標籤（v0.7，2026-09-26）

三項都是使用者明確要求：

1. **分組改為主辦方手動觸發**：`POST /api/activities/[id]/host/finalize`。截止時間到了**不會**自動做任何事——`loadActivity()` 不再呼叫任何結算邏輯，純粹讀取。DL 前也可以提前執行（執行後 `status` 變成非 `open`，組員的 PUT 志願就會被擋下）。沿用原本的 `claimFinalize`（搶 `open→finalizing` 鎖）確保只會成功執行一次；沒有「deadline」這個條件了，變成單純「主辦方按了才做」。
2. **已填寫名單**：`submissions` 表新增 `created_at`（第一次送出，之後不變）與 `updated_at`（最後一次修改）。`hostSubmissions()` 回傳姓名＋兩個時間戳＋是否修改過，**不含志願內容**，任何時候（截止前後、分組前後）都能呼叫。
3. **倒數標籤**：`countdown(ms)`（`src/lib/client.ts`）— ≤1 小時顯示「還剩 N 分鐘」、≤1 天顯示「還剩 N 小時」、≤3 天顯示「還剩 N 天」，這三段都是紅色標籤（`bg-danger/15 text-danger`）；超過 3 天維持原本的灰色「剩 d 天 h 小時」。主辦方和組員頁共用同一個 `ActivityHeader` 元件，所以兩邊都看得到。

**連帶的行為調整**：
- `useActivity()` 的自動重新整理邏輯從「截止後才每 2.5 秒狂 poll」改成「活動還在 `open` 狀態就每 15 秒 poll 一次」——原本的邏輯是等自動結算生效，現在沒有自動結算了，改成單純讓主辦方的填寫名單、組員看到的狀態能在分組後較快更新。
- 活動狀態文字從二態（填寫中／分配中…或已分配）改成三態：填寫中 → **已截止**（DL 到了但主辦方還沒按分組）→ 已分配。
- `/api/activities/[id]/submission` 的錯誤訊息拆成兩種，避免「已截止」這個字眼用在「其實是主辦方提前分組了、DL 根本還沒到」的情況：`主辦方已經執行分組，無法再修改` vs `已經截止填寫，無法再修改`。

**沒有做的事**：使用者也提到想看「誰還沒填」，但 v0.1 的 Q3 決定用自由填名字、不建立組員名單，所以系統並不知道「應該有誰」，只能列出「誰已經填了」。要做「誰還沒填」需要先做 Q3 的名單功能（主辦方先輸入預期成員名單），目前還沒做。
