# 人工複查清單 — 只要讀程式碼就能找到，`preflight-check.mjs` 抓不到

> 2026-09-26 第一次寫成，來自一次 `code-review` skill（high effort）掃過全專案的結果：
> 3 個真實 bug（已修，見下方「校準案例」）都是**純讀程式碼**找到的，不需要打開瀏覽器、
> 不需要建活動實測。`preflight-check.mjs` 檢查的是「build/lint/test 過不過、設定檔對不對」，
> 這份清單檢查的是「邏輯本身有沒有問題」——兩者互補，缺一不可。

## 怎麼用

每次改完 `src/lib/assign.ts`、`store.ts`、`service.ts` 或任何 API route 之後，把下面每一項
念過一遍、對照當次改動實際去讀那幾行程式碼確認。不是每次都要全部檢查——只檢查跟這次改動
有關的分類就好。

---

## A. `assign.ts` 演算法不變量

- [ ] **三種模式都要走過同一套事件記錄邏輯**：`bid`／`tier` 的單一志願分支（`opts.length===1`）
      跟 `pick` 的多職位分支（`opts.length>1`）是**兩段獨立的程式碼**，新增或修改其中一段時，
      確認 `full.push` / `tryTake` 成功 / `events.push({type:"yield"...})` 三種結果在**兩段**都有
      對應處理，不能只改其中一段。
      > 校準案例：多職位分支曾經完全沒有這三種記錄，`pick` 模式的搶奪永遠不會出現在主辦方看到的
      > 「分配過程紀錄」裡。
- [ ] **任何「隨機」都要重新確認是不是真的每次決定都重抽**：凡是註解寫「隨機」、「抽籤」、
      「coin flip」的地方，去確認對應的 `rng()` 呼叫或 tie-break map 是在**迴圈外算一次**
      （= 全域固定順序，只適合用在「這一整輪跑下來的人員優先序」這種本來就該固定的東西）還是
      在**每次要比較的當下**才算（= 真正獨立隨機，適合「這個人在多個平手選項間選哪一個」）。
      混用這兩種會讓「隨機」變成看似隨機、實則系統性偏袒某個選項。
      > 校準案例：`roleTie` 曾經在迴圈外算一次，導致所有人在同一個 seed 下對同一組平手職位
      > 都做出一樣的選擇。
- [ ] **`level`／`effectiveK` 的邊界是不是仍然一致**：改動放寬（relax）邏輯時，重新推一次
      「一個人被放寬之後，最終 `level` 一定 > k」這個不變量還成不成立（`assign.ts` 目前靠
      `for (lv=k+1; lv<maxRank(u); lv++)` 這個下界保證）。這個不變量壞掉的話，
      `relaxedCount` 跟實際的 `relax` 事件會對不上。
- [ ] **`maxMatchWithin` 跟實際 `assign()` 用的可接受範圍邏輯是不是同步**：這個函式是給 property
      test 用來算「理論最小放寬人數」的，如果 `assign()` 判斷「能不能落在前 k 順位」的邏輯改了
      （例如未來要支援每人可接受範圍不同），這個函式也要跟著改，不然 property test 會測到假的
      基準線，看起來通過其實沒測到真正的邏輯。

## B. `store.ts` / API route：交易與時間邊界

- [ ] **每一個「先讀、再判斷、再寫」的地方**：確認是不是用單一 SQL 陳述式（或 CTE）完成，
      不是「SELECT 一次 → 程式碼判斷 → UPDATE 一次」——後者在兩個請求同時進來時會有
      TOCTOU 競態。目前 `claimFinalize`、`updateActivity` 都是這樣做的，新增任何會改變
      `status` 的操作都要維持這個模式。
- [ ] **任何拿「現在的時間」跟「之前存的一個時間值」比較做驗證的地方**：問自己「如果這個值
      本來就沒有要改，光是使用者填表單、送出花掉的那幾十秒，會不會讓這個檢查從通過變成不通過？」
      如果會，確認呼叫端有沒有把「原本的值」傳進來，讓沒有要修改的情況跳過重新驗證。
      > 校準案例：編輯活動時，就算截止時間完全沒改，也會用「送出當下的現在時間」重新檢查
      > 「至少 1 分鐘後」，導致快到期時隨便改個敘述都會被擋。
- [ ] **狀態機的每一個「中間狀態」，是不是都有一條能離開它的路**：`status` 有 `open → finalizing → finalized`，
      `finalizing` 是「執行到一半」的鎖。問自己：如果程式在這個狀態被中斷（伺服器函式逾時、部署重啟），
      下一個請求走得到「接手／解鎖」的程式碼嗎？特別要檢查**呼叫端的前置條件**有沒有把中間狀態擋在門外——
      鎖的過期回收寫在 `claimFinalize` 裡，但入口如果只放行 `open`，那段回收邏輯就永遠是死碼。
      > 校準案例：改成「主辦方手動分組」後，`/host/finalize` 只放行 `status === "open"`，原本靠
      > `loadActivity` 自動觸發的過期鎖回收就走不到了，卡住的活動永遠回 409。
      > 順便檢查前端輪詢的停止條件（`useActivity` 的 `polling`）是不是也把中間狀態當成「已結束」。
- [ ] **`PgStore` 跟 `FileStore` 兩份實作是不是仍然行為一致**：兩個 class 各自獨立實作同一個
      `Store` 介面，改了其中一個方法（尤其是判斷條件、時間邊界）時，另一個要跟著改，不能只改
      一邊就以為兩邊都測過了（本機開發永遠只會測到 `FileStore` 那一份，`PgStore` 只有連正式
      資料庫才會被真正跑到）。

## C. API 驗證 / 授權

- [ ] **新增欄位時，`validatePrefs` 三種模式是不是都要更新**：`bid`／`tier`／`pick` 各自的
      驗證規則寫在同一個函式裡用 `if (mode === ...)` 分支，新增一種驗證規則時檢查是不是漏了
      某個模式（例如只在 `bid` 加了範圍檢查，卻忘了 `tier` 也需要）。
- [ ] **主辦方權杖跟組員權杖的檢查是不是都用 `tokenMatches`（timing-safe）**，不是直接用
      `===` 比字串——直接比較會讓伺服器的回應時間洩漏「猜對了幾個字元」的資訊。
- [ ] **任何回傳給前端的物件，重新讀一次它組出來的欄位**：確認沒有不小心把 `prefs`（志願內容）
      整包塞進 `publicView()` 或任何非 `hostDetail`／`hostSubmissions` 的回傳值裡。這個專案的
      核心賣點是「主辦方看不到志願內容」，任何新加的 API 欄位都要對照這條紅線檢查。

## D. 前端狀態同步

- [ ] **`useState(() => ...)` 的初始值是不是只在掛載時算一次**：`PrefForm`、`ActivityForm`
      這類元件如果之後改成會在使用者打字打到一半時被外部資料（例如 15 秒一次的 `useActivity`
      輪詢）重新整理，要確認會不會把使用者正在編輯、還沒送出的內容蓋掉。目前的設計是「初始值
      只吃一次 `initial` prop，之後不會被外部資料同步蓋掉」，這是刻意的，改動前先確認沒有
      意外破壞這個假設。
- [ ] **`useSyncExternalStore` 的 server/client snapshot 是不是真的可能不一樣**：
      `src/lib/viewport.ts` 的 server snapshot 固定回傳 `"desktop"`；如果之後手機版跟電腦版
      開始長得不一樣，第一次畫面（水合前）一律照 desktop 版渲染，掛載後才切到真正的裝置寬度，
      會有一次可見的畫面切換（目前因為兩版長得一樣所以看不出來）——真的讓兩版分岔時要考慮
      這個閃爍。

## 已知的競態（2026-09-26 複查時發現）

照 B 的第一條（先讀、再判斷、再寫）找到的競態，窗口都只有幾十毫秒（要兩個人同時操作）：

- ✅ **已處理（需執行一次 SQL）**：組員「儲存志願」跟主辦方「執行分組」同時發生 → 志願存進去卻不在結果裡；
  兩人同時搶最後一個名額 → 多出一人。修法是資料庫層 trigger（`docs/sql/harden-submissions.sql`，
  安裝步驟見 `docs/sql/README.md`）；沒執行前行為跟以前一樣。`/api/health` 的 `submissionGuard` 會顯示有沒有裝。
  Postgres 那份 SQL 用 PGlite（WASM 版 Postgres）驗證過邏輯；**鎖的並發行為本機無法測**（PGlite 只有單一連線），
  是依 Postgres 的列鎖語意（`FOR UPDATE` 與 `UPDATE` 互斥）設計的。
- ⏳ 主辦方 PATCH：讀 `count` 之後到 `updateActivity` 之間如果又有人送出，「人數上限不可少於已填人數」的檢查可能已過期。
  （名額 trigger 裝好後，之後的新增會照新的名額擋；影響只剩「剛好多出的那一人」。）
- ⏳ `myActivitiesView` 對每個活動各查一次 `countSubmissions`（N+1）；活動數多時可以改成一條 `GROUP BY`。
