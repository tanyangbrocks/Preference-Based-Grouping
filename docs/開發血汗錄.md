# 開發血汗錄

> 復刻自 `C:\SkillCreatorUE5\docs\開發血汗錄.md` 的機制（那個專案才是原始出處，不是作品集專案）。
> 記錄那些「程式碼看起來都對，測試也綠燈，但實際跑起來就是不對」的修羅場。一般 bug 的修法寫在 commit
> 訊息裡就夠了，這份檔案記的是**過程**——花了多久、走錯幾次、最後怎麼抓到的，給未來的人（不管是人類
> 還是 AI）一個警世故事。

---

## 什麼時候該加一案

- 一個 bug／怪現象花了不只一輪「猜測 → 改 → 重測」才抓到根因，中途排除過至少 2、3 個看起來合理但錯誤
  的假設
- 「看起來已經修好」但實際上沒修好，或修法本身建立在一個後來才發現是錯的假設上
- 排查過程中換過排查工具或方法（例如從純讀 log 換成瀏覽器 DevTools / React DevTools 逐層檢查渲染
  結果），而換工具正是破案關鍵
- 這個坑很可能不只咬過一次，或未來還會有人（人類或 AI）用同樣的錯誤假設再踩一次

**不需要記的**：單純讀程式碼、跑 `code-review` 或類似流程一次就抓到、當場就能理解根因並修好的一般 bug——
這種寫進 commit 訊息就好，不用佔這份檔案的篇幅。

## 格式

每一案至少包含：**症狀**（使用者實際看到什麼）、**排查過程**（走錯的路，包含為什麼當時覺得合理）、
**真正的根因**、**修法**、**教訓**（給未來的自己或其他 session）。
